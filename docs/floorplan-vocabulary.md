# The floorplan vocabulary in statehouse

How statehouse answers "where is this device?", what it deliberately declines to answer,
and what a consumer should read.

## The four fields

The devices namespace (`devices_home` for the `home` site) is generated by the
`floorplan` service, which owns the taxonomy. Statehouse relays three of its placement
facts, plus `part_of`, and derives none of them.

| Field | Meaning | Absent means |
|---|---|---|
| `room` | The floorplan room id the device **sits in**, e.g. `basement.kitchen`. | No room is known for this device — including the case where its readings describe the whole property (see `covers`). |
| `floor` | The floor id the device sits on, e.g. `basement`. | The namespace declared no floor. **UNKNOWN**, not "ground floor". |
| `covers` | What the readings **describe**, when that is not the room the device sits in: `house`, or another room id. | The device covers the room it sits in — the common case. |
| `part_of` | The id of the device this one is **part of**: the hot water cylinder a cylinder probe is inside, the fridge a fridge probe is inside. | The device is part of nothing — the common case. **Not** "its room comes from elsewhere": see below. |

Both `/state/devices` (and `/state`) and `/config/devices` carry all four, with the
same values for the same device. So do the retained MQTT payloads, which are built
by the same code as `/state`: `house/state/devices/{id}` and the `devices` map in
`house/state/snapshot`. A consumer may join the two endpoints on device id and
will not get two different answers.

That holds **by construction, not by convention**: both endpoints read placement from
the same stored device record. `/config/devices` deliberately does not read it from the
resolved profile, because the two are updated by opposite rules — the device record
merges so an absent field does not overwrite, while the profile is replaced wholesale on
every re-resolution, including the one a SIGHUP runs for every known device. Serving
placement from the profile made the endpoints diverge the moment a republished namespace
record stopped declaring a key. See `state.ProfiledDevice`, and
`TestPlacementStillAgreesAfterAReloadDropsTheNamespaceKeys` for the reload case.

One consequence worth relying on: **an absent key in a republished record means "not
republished", not "no longer in a room".** The last known placement survives. A device
genuinely moving rooms is expressed by publishing the new room, not by omitting the old
one.

### `floor` is declared, never derived

Room ids happen to be spelled `<floor>.<slug>` today, so it is tempting to split on the
first dot instead of reading `floor`. Statehouse does not, and neither do countinghouse
or greenhouse. Deriving it would put a second implementation of the floorplan's taxonomy
inside every consumer, each one silently disagreeing the moment a room id is spelled
unexpectedly. The floorplan publishes both facts; read both.

A device with a room but no declared floor is legal and must be handled.

### `covers` is why `room` can be empty

`room` and `covers` record two different facts, and conflating them was the original
defect. The electricity meter, central heating and hot water each sit in one room while
their readings describe the entire property:

```json
{ "id": "electricity_meter", "room": "basement.hallway",
  "floor": "basement", "covers": "house", "class": "energy_meter" }
```

A consumer grouping consumption by room must exclude or specially handle any device with
a non-empty `covers`, or it will attribute the whole property to that device's room.
Countinghouse does this with an explicit `IsWholeHouseTotal` predicate.

`house` is a coverage scope and a reserved series key — it is **never** a legal room id,
and statehouse will not publish it as one, including for a legacy `location: house`
record.

### `part_of` names an appliance, and never supplies a room

`part_of` (devices v0.2.0) says which appliance a device is part of. Its main use is
probes: a cylinder probe and a fridge probe are both `class: appliance_probe`, and the
class says their readings are **not ambient** (leave them out of room averages), but
not which appliance they describe. `part_of` does:

```json
{ "id": "hot-water-cylinder-top", "class": "appliance_probe",
  "room": "first.cupboard", "floor": "first", "part_of": "hot-water-cylinder" }
```

The two are complementary, not alternatives: filter on the class to exclude
non-ambient readings, read `part_of` to group a probe with its appliance.

**A device does not inherit its parent's room through `part_of`** (decided on
[#83](https://github.com/sweeney/statehouse/issues/83)). The shared library offers
`devices.PlaceOf`, which hands a probe with no `room` its parent's room, so the
namespace could omit it. Statehouse does not call it. Reading a room off another record
is deriving it, and statehouse relays placement, it does not derive it, for the same
reason `floor` is not split out of the room id. So a probe declares its own `room` and
`floor`, or has none here: `/state/devices` and `/config/devices` then omit them, and
the probe reads as UNKNOWN like any other unplaced device.

Because the shared vocabulary considers the omission legal, `devices.Check` does not
report it. Statehouse reports it itself, as an advisory warning when the devices
namespace is fetched (`statehouse.part_of_room_not_inherited`, from
`config.PartOfRoomNotInheritedProblems`). It is raised only when the answers would
actually differ: the device declares no place and its parent declares one. The device
is still applied. The message says what to add:

- parent has a room: `add "room": "first.cupboard", "floor": "first"` (floor only
  when the parent declares one);
- parent has only a legacy `location`: give the parent a room first. A free-text
  location is not a `<floor>.<room>` id, so copying it would only trade this warning
  for `device.room_malformed`.

The warning describes the **document**, not the running state. Because an absent key
keeps the last known value (below), a republish that drops a probe's `room` leaves
`/state` showing the old room while this warning says the record declares none. Both
are true; the fix is the same: declare the room in the namespace. The checks run over
every fetched document live in `config.DefaultDeviceChecks`, and all their problems
are logged sorted by device id.

`part_of` follows the same update rule as the placement fields: an absent key in a
republished record keeps the last known value, and a new value (the probe moved to
another appliance) replaces it. Statehouse relays `part_of`, it does not resolve it:
if the parent is removed from the namespace, the probe keeps relaying the now-dangling
id, and `devices.Check` warns `device.part_of_unresolved`. The parent itself (the cylinder, the
fridge) is usually a `telemetry: false` entry: it sends nothing, so it is never an
engine device and does not appear on either endpoint, so `GET` on the id a probe's
`part_of` names usually returns 404. **Treat `part_of` as a grouping key, not a
link.**

## `location` is deprecated

`location` is still present on both endpoints and carries exactly the same value as
`room`. It is the pre-floorplan spelling, and it conflated a floor, a room, a renamed
room and a coverage scope in one free-text field.

**New consumers should read `room` and ignore `location`.** It will be removed once the
last consumer has migrated; the phone app is the slowest lane because it ships through
Xcode.

The devices namespace no longer publishes `location` at all, so the value you see today
is always `room` passing through. The fallback is kept because a namespace that has not
been republished may still carry the old spelling, and because dropping it would break
consumers mid-migration.

## What statehouse does not relay

Each namespace record also carries a `coordinate` — the device's position inside the
house in metres, to three decimal places — and sometimes a free-text `note`. Statehouse
relays **neither**, and has no struct field for either, so no future DTO change can leak
them by accident.

This is data minimisation, not an oversight. Room and floor are the coarse placement a
consumer needs to group and label readings. A coordinate is a different kind of fact: it
locates a person's belongings to within a few centimetres of a specific spot inside their
home, and nothing consuming this API groups or labels by it. The floorplan service owns
it and renders it. `TestNamespaceCoordinateAndNoteAreNotRelayed` pins the boundary, so
adding either field is a decision a reviewer has to consciously approve rather than
something that slips in with a struct change.

Note also that room ids can themselves be personal — this property has rooms named after
the people who sleep in them. Combined with `/state`'s activity and occupancy data, the
placement vocabulary says who is where. Every endpoint carrying it requires a Bearer JWT;
only `/healthz` and `/openapi.json` are unauthenticated.

## Why room and floor are not Influx tags

They used to be. The `location` tag was deliberately removed (`b1a0d7a`, `78ef2bf`):
tagging points with a room bakes a device's placement into every historical point, so a
room rename rewrites history and a device that moves splits its own series. Room is now
resolved **at read time** from this API instead, which is part of why `/config/devices`
carrying `room` matters — it is how a reader maps stored points back to a place.

Do not add `room` or `floor` as Influx tags without revisiting that decision.

## Consumer notes

**`/config/devices` lists devices this instance has *seen*, not devices that are
configured.** It is built from the live store, so:

- A configured device whose adapter has not yet reported does not appear.
- A device that appears without being in the namespace has no `room`, `floor` or
  `covers` at all. On the `home` site today `schoolhouse-ups` is exactly this: matched by
  name hint, no namespace record, so no placement fields.

Treat a missing placement field as UNKNOWN and render it as such. Do not substitute a
default.

**Known limitation — service tokens are rejected.** `requireAuth` validates user access
tokens only; `identity/common`'s `Parse` explicitly refuses an `at+jwt` service token
("service token not accepted as user token"), and `ParseServiceToken` is never called. A
sibling service authenticating with `client_credentials` therefore gets a 401 from every
statehouse endpoint, including this one. That is a pre-existing gap, tracked separately —
it is not introduced by the placement fields, but it does limit who can use them today.

## Relationship to the sibling services

Countinghouse and greenhouse read the same `devices_home` namespace directly rather than
going through statehouse, and mirror `DeviceConfig` field for field so it round-trips.
All three services therefore answer in the same vocabulary about the same house, which is
the point — the floorplan owns the taxonomy, the services relay it, clients interpret it.

Fields the siblings carry that statehouse does not: `environment_fields` (greenhouse's,
describing which fields a sensor actually writes) and the `/rooms` and `/floors` catalogs
backed by the `floorplan_home` namespace. Statehouse does not read that namespace and has
no catalog endpoints.
